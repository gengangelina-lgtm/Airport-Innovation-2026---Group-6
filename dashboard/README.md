# HermesTC — Gate Operations Dashboard

A web dashboard for the gate-assignment subproblem, built from the
"Pearson Gate Management Dashboard" Figma Make design. It replays any scenario in
`../gate-sorting-algorithm/flight_data/` through **Group 6's algorithm (`sol.py`)**
and shows operators what is happening at every gate, and why.

## Run it

```bash
cd brock-solutions/gate-assignment-subproblem/dashboard
npm install
npm run dev
```

Open the local address it prints (usually http://localhost:5173).

| Command | What it does |
| --- | --- |
| `npm run dev` | Start the dashboard with live reload |
| `npm run build` | Build a static site into `dist/` (open `dist/index.html` or host it anywhere) |
| `npm run check:engine` | Run the algorithm over every scenario and print status / score (add `-- -v` for the full log) |
| `npm test` | Engine test suite: replays every scenario and checks the hard rules after each update, then fuzzes random operator actions (`FUZZ_RUNS=600 SEED=7 npm test` for a longer run) |

## Screens

| Screen | Shows |
| --- | --- |
| **Current Hour** | Every gate at the simulation time: current and incoming flight, delays, equipment swaps, emergencies, outages and why a flight was moved. List or map view. |
| **Full Day Schedule** | Gate timeline with outages, former assignments, the soft score + breakdown, and an operations log of each decision. |
| **Unassigned Flights** | Flights the algorithm could not place safely, with the reason and time remaining. |
| **Planes at Pearson** | Aircraft occupying a gate or holding at the simulation time. |

The bar under the header is the **simulation clock**: drag it, press play, or click a
marker to jump to a message time (planning, delay, outage, diversion…).

## Operator actions (fed back into the algorithm)

- **Current / Incoming Manual Update**: move a flight to another gate (suggestions are
  ranked by `sol.py`'s `gate_cost`; incompatible or occupied gates are disabled with the
  reason) and/or change its gate-window time (sent as an `UpdateTiming` message).
- **Unassign from gate**: takes a flight off its gate; it waits in Unassigned Flights (the
  auto re-plan leaves it alone) until someone assigns it a gate.
- **Mark out of service**: injects a 2-hour `GateOutage` at the current time. If planes are at or
  due at the gate during the outage, a pop-up lists them with a suggested gate each (best free
  gate by the algorithm's cost) so they can be reassigned in one step, or left unassigned.
- **Put back in service**: ends an outage (from the scenario or an operator) at the current time.

After each action the whole scenario is re-simulated, so the algorithm re-plans any
affected flights and the score updates. **Reset** removes all operator changes.

## How it works

| File | Purpose |
| --- | --- |
| `src/engine/model.ts` | Port of `gms/` (messages, presence intervals, classification, compatibility) |
| `src/engine/solver.ts` | Port of Group 6's `sol.py` (cost function + branch-and-bound batch search) |
| `src/engine/simulate.ts` | Port of `evaluator.py`'s `run_sim`, recording a snapshot per message time |
| `src/ops.ts` | Turns a snapshot into gate rows, unassigned reasons, suggestions |
| `src/data/repoData.ts` | Loads `static_info.json` and every `flight_data/*.json` directly from the repo |
| `src/data/pearsonMap.ts` | Overhead outline of Pearson (terminals, aprons, runways, taxiways) generated by `scripts/build_map.py` from OpenStreetMap data |
| `src/App.tsx`, `src/index.css` | The screens, styled from the Figma design |

The TypeScript engine produces the same results as the Python evaluator on the sample
scenarios (all 12 run with zero hard failures). **If you change `sol.py`, mirror the change in
`src/engine/solver.ts`.** New scenario files in `flight_data/` show up automatically.

Unlike the Python evaluator, when a flight's gate becomes invalid (outage, conflict, aircraft no
longer fits) and the algorithm finds no other compatible gate, the dashboard moves that flight to
Unassigned Flights instead of failing, so the operator can see it and assign it manually.

## Map data

The map view uses an overhead outline of Toronto Pearson generated from
[OpenStreetMap](https://www.openstreetmap.org/copyright) data (© OpenStreetMap contributors, ODbL).
Challenge gates are placed on the matching real piers: D1–D3 on Pier D, I1–I4 on Pier E,
C1–C2 on the Cargo West apron.

## Stress-test days

`scenarios/` holds three extra days generated by `scripts/make_scenarios.py` (reproducible, fixed
seeds), kept separate from the challenge's `flight_data/`:

| Day | What it tests |
| --- | --- |
| **Super busy day** (64 flights) | Full-day schedule 05:30–01:00 with delays, two outages, two diversions, an equipment swap and cancellations |
| **Overload crunch** (31 flights) | 30 turnarounds in 4 hours — more than the gates can hold, so flights must be left unassigned |
| **Storm day** (43 flights) | Cascading delays, three outages (one open-ended), three diversions, equipment swaps and cancellations |

## Testing

`npm test` checks, at every update of every scenario:

- no two aircraft overlap at a gate · every aircraft fits its gate (wingspan, jetbridge, cargo / customs)
- nothing sits on a gate during an outage · cancelled, held or displaced flights hold no gate
- no flight is left waiting while a compatible gate is free (operator-held flights excepted)
- the original 12 sample scenarios keep their exact evaluator scores · replays are deterministic

then repeats the checks after thousands of random operator actions (moves, unassigns, outages,
restores, retimes). Last full run: ~63 million checks over ~92,000 random actions, all passing.

### Fixes made to the algorithm (vs `sol.py`)

The busy days exposed cases where `sol.py` produced invalid plans (the sample scenarios are too
small to trigger them). They are fixed in `src/engine/solver.ts` / `simulate.ts`, marked
`HermesTC fix`, and leave the sample-scenario results unchanged:

1. A changed flight that can't be re-placed was dropped from the working plan, so its gate could be
   given to another flight while the aircraft was still there. It now keeps its booking, and the
   placement re-runs until no new flight gets stuck.
2. The single-gate fallback could pick a gate the batch search had already given to a later flight.
   Batch choices are now booked before any fallback.
3. Reassignments are applied together (all moving flights lifted first), and flights that changed
   but stay put are updated to their new times before anything is checked against them.
4. If a flight is taken off a gate, waiting flights get a second chance at the gate it freed.
